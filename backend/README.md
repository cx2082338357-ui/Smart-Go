# Smart1智慧校园————基于微调大模型的智慧校园小程序

本文档从**产品功能**与**后端实现**两方面说明当前仓库中的智慧校园解决方案：前端为微信小程序，业务 API 由 **`backend/main.py`**（FastAPI）提供；可选 **`ai_service`** 承载基于校园知识微调的大模型推理与检索增强。

---

## 功能模块

### 1. AI 智能助手

本模块是「Smart1」品牌的核心亮点：**日常事务类问题**尽量秒回，**开放域问题**交给微调大模型；在网络不稳或服务未启动时仍能给出可读的回答，保证服务体验的连续性。

#### 1.1 对话形态与适用场景

| 形态 | 接口 / 通道 | 适用场景 |
|------|----------------|----------|
| 非流式 HTTP | `POST /api/ai/chat` | 小程序简单一问一答、希望一次拿到完整 JSON |
| 流式 SSE | `POST /api/ai/stream` | 需要打字机效果；隧道（如部分 ngrok 免费版）**不支持 WebSocket** 时优先用 HTTP 长连接推送 |
| WebSocket | `WS /api/ai/stream/ws` | 客户端发送一条 JSON（含 `message`、`history`、`conversationId`），服务端按块推送与 SSE 兼容的文本帧 |

历史对话一般通过请求体中的 **`history`** 传入；服务端会为会话生成或沿用 **`conversationId`**，便于前端串联上下文。

#### 1.2 两级响应策略（关键词 → 大模型）

1. **关键词 / 规则优先**  
   - 非流式接口内建较大规模的「关键词 → 固定话术」表，覆盖：**学分与毕业**、**成绩单与选课**、**学生证与请假**、**一卡通与报修**、**课表与考试**、**图书馆与食堂**、**空教室**、**奖学金与社会实践**等校园高频意图。  
   - 命中后会有**短延迟**（贴近真实推理节奏），并附带 **`quickActions`**（如跳转成绩页、课表页、考试页等小程序路径），提升「助手 → 办事」闭环体验。  
   - **学分、毕业、GPA、绩点、成绩**等与学生个体相关的文案，会读取请求头 **`Authorization`**，通过 `academic_mock.parse_student_id_from_auth` 解析当前登录身份；后端按配置切换两套学业话术（已修学分、GPA、排名等），并与成绩模块返回的数据保持一致。

2. **调用微调大模型（`ai_service`）**  
   - 未命中关键词时，非流式接口使用 **httpx** 向 **`http://localhost:8001/chat`** 发送 JSON：`question`、`role`（如 student）、`session_id`、`category_filter` 等，超时时间设为 **180 秒**，避免本地推理被误判为失败。  
   - 流式路径统一走 **`ai_bridge.generate_ai_stream`**：内部同样先尝试基于关键词的规则流式输出；否则请求 8001，将返回的完整 **`answer`** 按固定长度（约十余字符）切块，封装为 **SSE** 的 `data: {...}` 行推送，并在末尾发送 **`[DONE]`**。  
   - 若连接失败、超时或非 200：自动 **降级** 为规则回答或非流式接口中的 **固定引导语**（介绍助手能力范围），避免前端白屏或长时间挂起。

#### 1.3 附属能力

- **热门话题**：`GET /api/ai/hot-topics`，用于会话页快捷 chips。  
- **会话生命周期**：保存、结束等接口便于前端串联会话管理流程。  
- **反馈**：`POST /api/ai/feedback`，接收用户对某条回复的评价（当前可仅存于内存）。  
- **对话历史查询**：`GET /api/ai/history`（若与前端约定一致可做列表展示）。

### 2. 教务与学习服务

教务相关数据在当前工程中为 **结构化本地数据集**：不依赖外部教务系统实时接口，字段设计与前端页面一致，便于贯通「课表 → 成绩 → 考试 → 空教室」完整学习场景。

#### 2.1 课表

- **周课表**：`GET /api/schedule/week`，返回指定周次的课程单元（节次、教室、教师等示例字段）。  
- **当日课表**：`GET /api/schedule/today`，突出「下一节课」类首页场景。  
- **学期信息**：`GET /api/schedule/semester-info`，当前学期周次、起止日期等元数据。  
- **上课提醒**：`POST /api/schedule/reminder` 与取消接口，覆盖「订阅提醒」交互（后端可为内存标记或空操作，以前端体验为主）。

#### 2.2 成绩与学业画像

- **摘要**：`GET /api/score/summary`，汇总 GPA、总学分要求、已修学分、平均分、毕业进度百分比等。  
- **学期列表**：`GET /api/score/semesters`，下拉切换学期。  
- **明细**：`GET /api/score/list`，按学期返回课程名、学分、分数、必修/选修等。  

**重要机制**：上述接口根据 **`Authorization` Bearer Token** 解析出的身份，在 **基准学业档位** 与 **其它档位** 之间切换两套数据集（逻辑见 `main.py` 与学业策略模块 `academic_mock.py`）。同一套前端，不同绑定账号可对应不同学业曲线，体现个性化展示。

#### 2.3 考试安排

- `GET /api/exam/list`：返回近期考试科目、时间、地点等列表，与 AI 助手中「考试」关键词话术相互印证。

#### 2.4 空教室查询

- **楼栋热力 / 列表**：`GET /api/classroom/heatmap`、`GET /api/classroom/available`。  
- 数据由模板生成多栋教学楼、多间教室的 **总座位数 / 空闲座位 / 空座率**，用于热力图与列表筛选展示。

### 3. 用户认证与个人中心

#### 3.1 登录与教务绑定

- **简易登录**：`POST /api/auth/login`，传入用户名（可与教务账号一致），返回带时间戳的 Token 及基础 `userInfo`。  
- **教务绑定**：`POST /api/auth/bind`，校验账号标识 + 明文密码是否与后端配置的 **SHA256 摘要**一致；成功则签发 Token 并返回完整学籍字段（学院、专业、班级等）。  

账号与口令由后端内存配置维护；正式环境需替换为统一认证中心或学校 OAuth。

#### 3.2 手机号与微信（扩展登录）

- **手机号验证码**：发送验证码、手机号登录等接口构成完整 UI 流程；验证码校验可采用固定规则或简化策略。  
- **微信登录**：使用 `code` 换取会话侧用户信息，呈现一键登录与头像昵称流程。  
- 内存中的 **`_sessions`**、**`_phone_to_student`** 等用于区分「已绑定 / 未绑定教务」两种返回结构。

#### 3.3 首页与个人数据

- **`GET /api/user/stats`**：返回与当前学号一致的学分、GPA、进度等，供首页卡片展示；需前端在请求头携带绑定后的 Token。

### 4. 校园社区

#### 4.1 内容与互动

- **列表**：`GET /api/community/posts`，支持分页或筛选（具体参数以前端调用为准）。  
- **发布**：`POST /api/community/posts`，传入正文、图片 URL 列表、手动标签等；服务端写入内存列表 **`_community_posts`**。  
- **点赞**：`POST /api/community/like`，切换点赞状态。

#### 4.2 轻量「AI 标签」

发布帖子后，服务端根据正文关键词（如「丢失」「捡到」「美食」「图书馆」「兼职」等）映射到 **话题标签**（如 `#寻物启事`、`#美食推荐`），最多截取若干条作为 **`aiTags`** 返回。该逻辑规则简单、延迟可控，用于体现「社区 + AI」结合能力；若需更高质量标签可改为调用同一 `ai_service` 的分类接口。

---

### 5. 寻物启事与匹配

#### 5.1 列表与详情联动

- **列表**：`GET /api/lost-found/list`，参数包括 **`type`**（`lost` / `found`）、**`page`**、**`limit`**。  
- **关键设计**：详情页往往只持有全局 **`id`**，列表若按类型过滤可能导致当前 id 不在本页数据中。后端支持 **`type=all`** 或 **`type=any`**：返回 **失物 + 招领的全集**（仍分页），保证详情页能通过 id 命中记录。  
- 每条记录附带 **`isMatch`**：表示是否在简易匹配算法中与另一类启事建立关联，用于角标或筛选。

#### 5.2 发布与匹配列表

- **发布**：`POST /api/lost-found/publish`，生成 UUID、写入 **`_lost_found_items`** 首部，返回新 id。  
- **匹配列表**：`GET /api/lost-found/matches`，按类型返回可能配对条目及汇总数量，供「匹配提醒」类 UI 使用。

---

### 6. 校园商城

#### 6.1 数据来源与分类

- 商品数据持久化在 **`backend/data/tmall_products.db`**（SQLite），通过 **`main.py`** 中的 **`get_db()`** 上下文管理连接；路径相对于 **`main.py`** 所在目录，避免写死机器盘符。  
- 原始数据中类目字段可能为空，后端使用较长 **`CASE WHEN`** SQL 表达式，根据 **标题关键字** 推导展示分类：**杯壶、零食、饮料、糕点、坚果** 等，并排除易误判词（如「巧克力」归入零食而非饮料）。

#### 6.2 接口能力

- **商品列表**：`GET /api/shop/products`，支持分类、排序、分页（与前端商城 Tab 对应）。  
- **详情**：`GET /api/shop/product/{product_id}`。  
- **分类**：`GET /api/shop/categories`，与推导类目对齐。  
- **图片 URL**：优先 `main_pic`，其次解析 JSON 多图字段，最后回落到 **分类默认图**（若挂载了 `/assets` 静态目录）。

#### 6.3 下单

- **`POST /api/shop/create-order`**：根据购物车条目计算总价，生成订单号，写入内存订单列表，并返回小程序侧发起支付所需的 **`payment` 结构**，贯通「提交订单 → 收银台」流程。

---

### 7. 订单与支付

#### 7.1 订单数据来源

- 服务启动时执行 **`_generate_db_orders()`**：尝试从 SQLite **随机抽取**商品行，组合为多商品订单，状态覆盖 **待付款、配送中、待收货、已完成** 等；若数据库不可用则回退到内置备用订单列表。  
- **再来一单**：`POST /api/order/reorder` 根据历史订单复制条目生成新订单（简化实现）。  
- **列表与统计**：`GET /api/order/list`、`GET /api/order/counts`。

#### 7.2 支付与售后流程

- **发起支付**：`POST /api/order/pay`，查找内存订单，组装微信 **JSAPI** 所需的 `timeStamp`、`nonceStr`、`package`、`signType`、`paySign`；内部可尝试请求微信统一下单，失败或无配置时返回可供本地调试的预付单标识及布尔标记字段，前端可据此跳过真实 `wx.requestPayment`。  
- **取消 / 确认收货 / 删除 / 评价**：对应 POST 接口更新状态或返回成功提示，便于完成业务闭环。

---

### 8. 校园配送

#### 8.1 骑手侧

- **可接订单池**：`GET /api/delivery/available-orders`，返回待抢单列表（内存生成）。  
- **申请成为骑手 / 状态查询**：`POST /api/delivery/apply-rider`、`GET /api/delivery/rider-status`。  
- **接单**：`POST /api/delivery/accept`。

#### 8.2 用户侧配送下单与快捷选品

- **`POST /api/delivery/create`**：提交收货地址结构体、商品明细、备注、运费与总价，生成配送订单并写入 **`_order_store`**，返回订单号。  
- **`GET /api/delivery/quick-goods`**：从 SQLite 中按 **销量** 与品类（零食、饮料、杯壶等）选取少量商品，作为配送页「快捷加购」数据源。

---

### 9. 系统与调试辅助

- **`GET /health`**：返回健康状态、时间戳、本机探测 IP、监听端口等，便于运维脚本探活。  
- **`GET /api/system/local-ip`**：返回建议的 **`baseUrl`**（如 `http://{局域网IP}:8080`），配合小程序 **设置页填写 API 地址**，解决真机无法访问 `localhost` 的问题。  
- **`POST /api/analytics/track`**：接收页面与行为埋点（可选上报）。  
- **CORS**：当前对来源较为宽松，便于开发；上线需改为白名单域名。  
- **静态资源**：若本机存在小程序 `assets` 目录，应用可将 **`/assets`** 挂载为静态文件服务，供商品默认图等访问（路径以运行环境为准）。

## 后端工程说明（与本仓库一致）

### 架构关系

小程序 **HTTPS / 局域网 HTTP** 访问 **`backend`（8080）**；`backend` 在需要时 **HTTP** 调用 **`ai_service`（8001）**。教务、社区、寻物、订单主体为 **进程内内存**；商城商品与部分订单生成依赖 **SQLite**。

### 目录与核心文件

```
backend/
├── main.py              # FastAPI 应用、全部路由、内存数据集、SQLite 访问、微信支付降级与兼容逻辑
├── academic_mock.py     # Bearer 解析身份；基准与其它档位的学业摘要（供 AI 话术）
├── ai_bridge.py         # 流式生成：关键词规则 → 调用 8001 → SSE 分块与转义
├── core/                # config / security / database（异步 SQLAlchemy 模板，主流程可选）
├── data/
│   └── tmall_products.db
├── requirements.txt
└── README.md
```

### 响应约定

- 多数业务接口：`{ "code": 0, "data": ... }` 表示成功；非 0 `code` 搭配 `message` 表示业务错误。  
- 需要按登录身份分流的接口：客户端应在 Header 携带 **`Authorization: Bearer …`**（与登录 / 绑定接口返回的 Token 格式一致）。

### 安全边界（必读）

- 口令当前仅存 **SHA256**，无盐、无防爆破；Token 非标准 JWT，**严禁用于生产**。  
- 微信与支付相关密钥在仓库中多为示例配置，真实调用需替换并走服务端保密配置。

### 快速启动

```bash
cd backend
pip install -r requirements.txt
python main.py
```

- **Swagger / OpenAPI**：`http://127.0.0.1:8080/docs`  
- **可选**：在项目根目录启动 **`ai_service`**（监听 **8001**），使开放域问题走微调模型；否则依赖关键词与降级文案仍可完整跑通核心流程。

### 真机联调建议

- 手机与 PC 处于同一局域网，或使用内网穿透 **HTTPS** URL；小程序需在后台配置合法域名或开启开发者工具「不校验域名」。  
- 小程序 **API Base URL** 必须使用电脑局域网 IP + **8080**，不能使用 `127.0.0.1`。
